  ✶ Insight ─────────────────────────────────────
  - WebConfig gets basePath through its constructor using @Value, not by field
    injection. That lets you build the class directly in a plain unit test
    without starting Spring.
  - @WebMvcTest loads only the web slice, and in Spring Boot 4 it doesn't pick

    makes /api/v1/... match in the test. Without it, the test that calls
    /accounts/1/limits without the prefix would get 200 instead of 404.
  - The controller only maps service output to LimitsResponse through
    LimitsResponse.from(...). Business rules like "does this account exist?"
    belong in AccountService.

  Request: /api/v1/accounts/0/limits or /-5/limits
  What happens: @Positive fails and Spring throws
    HandlerMethodValidationException. The controller method never runs, so the
    service isn't called.
  Status: 400

  What happens: abc can't be converted to a Long, so

  Status: 400

  What happens: The URL doesn't match the route at all
  Status: 404

  ✶ Insight ─────────────────────────────────────
  - I deliberately left @Validated off the controller. Since Spring 6.1 (and in
    Boot 4), Spring MVC validates constraint annotations on controller
    parameters by itself and returns 400. Adding @Validated to the class
    switches to the older AOP-based validation, which throws
    ConstraintViolationException. That exception isn't handled by default, so
    the client gets a 500. This trips up a lot of people.
  - @NotNull doesn't do much here. A @PathVariable is required by default, so a
    request without the segment never reaches the method; it fails route
    matching. I kept it because it documents intent and protects the method if
    someone later calls it directly or marks the variable required = false.
  - Plan for your @ControllerAdvice: right now the 400 bodies are Spring's
    default error format. In the global handler, add @ExceptionHandlers for
    HandlerMethodValidationException (field-level messages come from
    ex.getParameterValidationResults()) and for
    MethodArgumentTypeMismatchException. Another option is to extend
    ResponseEntityExceptionHandler, which already handles the first one and
    returns ProblemDetail.

     Plan: Real transfer logic in TransferService with business-rule exceptions

     Context

     POST /api/v1/transfers currently has a skeleton TransferService.transfer(),
     which only echoes the request back.

     The user wants real logic, for the source account only:
     1. The source account must exist (id=1).
     2. The amount must not exceed the balance.
     3. The amount must not exceed the remaining transfer limit.
     4. If all checks pass, the source balance and transfer limit are both
        reduced.

     Each broken rule should throw an appropriate exception.

     Answer to "one exception or one per rule?": one exception per rule, under a
     shared base class.
     - Separate types let the API tell the client why a transfer failed. Later,
       your @ControllerAdvice can map each one to its own error code
       (INSUFFICIENT_FUNDS, TRANSFER_LIMIT_EXCEEDED), and tests can assert the
       exact reason.
     - The shared base TransferRejectedException means one handler (and one HTTP
       status) can still cover every rejected transfer.

     The existing pieces to reuse:
     - AccountService.getAccount(Long) already throws AccountNotFoundException
       (404).
     - Limits.isTransferLimitExceeded() and Limits.subtractTransfer() are in
       model/Limits.java.
     - MoneyUtils.normalize is in util/MoneyUtils.java.
     - Account.setBalance already normalizes the value.

     Changes (base package com.example.banking)

     1. exception/TransferRejectedException.java: an abstract class extending
        RuntimeException
        - Annotated @ResponseStatus(HttpStatus.UNPROCESSABLE_CONTENT) (422). The
          request is valid, but the business rules refuse it.
        - Subclasses inherit the annotation, since Spring looks it up with
          merged-annotation search.
        - Like AccountNotFoundException, the annotation is temporary until the
          global @ControllerAdvice exists.
     2. exception/InsufficientFundsException.java extends the base. Constructor
        (Long accountId, BigDecimal amount, BigDecimal balance), with the
        message "Account 1 has insufficient funds: requested 60000.00, available
        50000.00".
     3. exception/TransferLimitExceededException.java extends the base.
        Constructor (Long accountId, BigDecimal amount, BigDecimal 
        remainingLimit), with a similar message.
     4. model/Account.java: add boolean hasSufficientFunds(BigDecimal amount),
        which is balance.compareTo(amount) >= 0. It mirrors
        Limits.isTransferLimitExceeded. Add a test case in AccountTest.
     5. service/TransferService.java: transfer(request)
        - Normalize the amount, then call accountService.getAccount(sourceId).
          That call gives the 404 for an unknown account.
        - Checks (TODO(human), ~6 lines): run both rule checks and throw the
          matching exception. Your decision is the order of the checks, which
          affects the message a client sees when both rules fail.
        - The mutation runs only after all checks pass, so a rejected transfer
          leaves the state untouched:
          - source.setBalance(source.getBalance().subtract(amount))
          - source.getLimits().subtractTransfer(amount)
        - The checks and the mutation sit together in a synchronized (source)
          block. Two concurrent requests then can't both pass the check against
          the same old balance. (The account is a shared singleton field, as
          discussed earlier.)
        - The target account is not touched (out of scope for now). Return a
          TransferResponse as before.

  ✶ Insight ─────────────────────────────────────
  - Separate types plus a shared base let you choose how detailed to be. Your
    future @ControllerAdvice can have one
    @ExceptionHandler(TransferRejectedException.class) for every refusal. You
    can also add specific handlers that return error codes such as
    INSUFFICIENT_FUNDS, and Spring picks the closest matching exception type.
    Tests can already check the exact reason with
    assertThrows(InsufficientFundsException.class, ...).
  - Spring finds @ResponseStatus on the parent class. It searches the class
    hierarchy, so the subclasses don't need their own annotation.
  - Check everything first, then change state. If the balance were reduced
    before the limit check failed, the account would be left half-updated. The
    synchronized (source) block keeps the checks and the update together, so two
    simultaneous requests can't both pass against the same old balance.

  ✶ Insight ─────────────────────────────────────
  - Ask who wrote the message. If your code wrote it, as in your domain
    exceptions, getMessage() is safe to return. If a framework wrote it, like
    Spring or Jackson, it's debug output that can reveal internals, so extract
    what you need. For the same reason, the malformed-JSON handler returns a
    fixed message rather than Jackson's parser error.
  - The order of errors isn't guaranteed. Hibernate Validator collects
    violations in an internal set, so without the .sorted(...) the message could
    come out in a different order between runs. That's why the test listing two
    fields can check an exact string.
  - A good next step: if clients will need to show errors next to form fields,
    you could add a list of {field, message} objects to ErrorResponse instead of
    one joined string. It's a small change in this same method.
