     Plan: Account model with hardcoded Limits

     Context

     banking-system-sample is a fresh Spring Boot 4.1.2 / Java 25 project with
     Lombok, and it has no domain classes yet. This change adds the first model:
     an Account with an id, a balance and a Limits object. Every value is
     hardcoded through a no-arg constructor so other code can use it right away.

     Hardcoded values (confirmed with the user)

     - id = 1
     - balance = 50000
     - limits: cardPayments = 5000, cash = 2000, internetPayments = 5000,
       transfer = 10000

     Files to create

     Both classes go in the model package, at
     src/main/java/com/example/banking/model/. Each file starts with package 
     com.example.banking.model;.

     1. Limits.java
        - Fields: BigDecimal cardPayments, cash, internetPayments, transfer
        - Lombok @Getter, @Setter and @AllArgsConstructor
        - A no-arg constructor that sets the four hardcoded defaults above
     2. Account.java
        - Fields: Long id, BigDecimal balance, Limits limits
        - Lombok @Getter, @Setter and @AllArgsConstructor
        - A no-arg constructor: id = 1L, balance = new BigDecimal("50000"),
          limits = new Limits()

     Design notes:
     - BigDecimal is used for money so there are no floating-point rounding
       errors.
     - Each Account gets its own Limits instance, so changing one account's
       limits can't affect another's.
     - The all-args constructors are kept so real data can be loaded later.

● ✶ Insight ─────────────────────────────────────
  - An OperationType enum lets a caller like a future TransferService call
    limits.subtract(OperationType.TRANSFER, amount). The alternative is four
    almost identical methods, one per limit.
  - The arrow-form switch on an enum doesn't need a default. Because subtract
    uses it as a statement, adding a new enum constant won't cause a compile
    error; it will just do nothing. Use it as an expression (returning a value)
    if you want the compiler to force you to handle every constant.
  - BigDecimal is immutable: remaining.subtract(amount) returns a new object and
    leaves remaining unchanged. That's why each case assigns the result back to
    its field.
    ─────────────────────────────────────────────────

  I've added three pieces to the model package:
  - OperationType.java: an enum with CARD_PAYMENT, CASH, INTERNET_PAYMENT and
    TRANSFER.
  - LimitExceededException.java: an unchecked exception whose message names the
    operation, the amount and the remaining limit.
  - Limits.subtract(type, amount): picks the right limit for the operation type
    and passes it to a private deduct method, which is still a placeholder.
    Until you fill it in, any call to subtract throws
    UnsupportedOperationException.

    gives 3. Choose whether to reject such amounts or round them with

    after checking the limit.

> does substract method keep 2 point precision correctly?                       

● Only when the amount has 2 or fewer decimal places. subtract doesn't enforce 2
  decimal places on its own.

  BigDecimal.subtract gives a result with as many decimal places as the operand
  that has more of them:

  ┌──────────────────────────────────────┬─────────┬──────────┬─────────────┐
  │               transfer               │ amount  │  Result  │  Decimal    │
  │                                      │         │          │   places    │
  ├──────────────────────────────────────┼─────────┼──────────┼─────────────┤
  │ 10000.00                             │ 100     │ 9900.00  │ 2 ✅        │
  ├──────────────────────────────────────┼─────────┼──────────┼─────────────┤
  │ 10000.00                             │ 1500.5  │ 8499.50  │ 2 ✅        │
  ├──────────────────────────────────────┼─────────┼──────────┼─────────────┤
  │ 10000.00                             │ 1500.50 │ 8499.50  │ 2 ✅        │
  ├──────────────────────────────────────┼─────────┼──────────┼─────────────┤
  │ 10000.00                             │ 0.005   │ 9999.995 │ 3 ❌        │
  ├──────────────────────────────────────┼─────────┼──────────┼─────────────┤
  │ 10000 (set through the setter or     │ 100     │ 9900     │ 0 ❌        │
  │ all-args constructor)                │         │          │             │
  └──────────────────────────────────────┴─────────┴──────────┴─────────────┘

  So with the hardcoded default (10000.00) and normal amounts, the result keeps
  2 decimal places. There are two ways to lose that:
  1. The amount has more than 2 decimal places. The extra digits carry into the
     remaining limit.
  2. transfer is set without 2 decimal places. The Lombok setter and the
     all-args constructor accept any BigDecimal.

  A simple fix is to round the result back to 2 decimal places:
  public void subtractTransfer(BigDecimal amount) {
      transfer = transfer.subtract(amount).setScale(2, RoundingMode.HALF_EVEN);
  }
  HALF_EVEN is "banker's rounding": a tie goes to the nearest even digit, so
  9999.995 becomes 10000.00. If you'd rather reject amounts like 0.005 than
  silently round them, throw an exception when amount.scale() > 2.

  ✶ Insight ─────────────────────────────────────
  - Rounding the result fixes this method, but the setter and constructor can
    still store a different number of decimal places. A setter of your own that
    calls setScale(2, ...) would enforce it everywhere.
  - For money, rejecting an amount with too many decimals is often safer than
    rounding it, because rounding can quietly create or lose fractions of a
    cent.
    ─────────────────────────────────────────────────

  Should I add the setScale fix, or the version that rejects such amounts?
