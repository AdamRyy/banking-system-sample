     Plan: Required Authorization + X-Correlation-Id headers, and no default 
     error responses

     Context

     banking-system-sample (Spring Boot 4.1.2, Java 25) has two endpoints, GET 
     /api/v1/accounts/{id}/limits and POST /api/v1/transfers. They currently
     accept any request. The user wants every request to carry:
     - Authorization: Bearer <token>, where the token is a hardcoded value. If
       it is missing, malformed or wrong, the app returns 401.
     - X-Correlation-Id, any non-blank value (it is not compared with a fixed
       value). If it is missing or blank, the app returns 400, because it's a
       malformed request, not an identity problem.

     Also, no default Tomcat or Spring Boot error responses (HTML or whitelabel
     JSON) should ever reach the client. Every error should use the app's
     ErrorResponse JSON. The user confirmed the 400/401 split and the "token
     must match, correlation id only needs to be present" rule.

     Existing pieces this plan reuses:
     - exception/GlobalExceptionHandler.java: the build(ErrorCode, message)
       helper and the Exception catch-all
     - exception/ErrorCode.java: an enum that ties each code to its HTTP status
     - dto/ErrorResponse.java: already has a reserved
       @JsonProperty("X-Correlation-Id") correlationId that is always null for
       now
     - config/WebConfig.java: a WebMvcConfigurer that already holds @Value
       config, where the interceptor will be registered

     Approach

     1. Config (src/main/resources/application.properties)

     app.security.token=token-123
     The value is hardcoded, but kept in properties rather than in the code.

     2. New exceptions (exception/ package, same style as 
     AccountNotFoundException)

     - UnauthorizedException: missing or invalid bearer token
     - MissingCorrelationIdException: missing or blank X-Correlation-Id

     3. ErrorCode: add

     - UNAUTHORIZED(HttpStatus.UNAUTHORIZED)
     - MISSING_CORRELATION_ID(HttpStatus.BAD_REQUEST)

     4. New config/RequestHeadersInterceptor.java (implements 
     HandlerInterceptor)

     - Constants: AUTHORIZATION, CORRELATION_ID = "X-Correlation-Id",
       BEARER_PREFIX = "Bearer "
     - The constructor takes the expected token.
     - preHandle: validates both headers and throws the matching exception. If
       the correlation id is present, it is echoed back in the response header.
       The user writes the validation logic (TODO(human), see below).

     5. WebConfig: register the interceptor

     - addInterceptors: registry.addInterceptor(new RequestHeadersInterceptor(to
       ken)).addPathPatterns("/**").excludePathPatterns("/error")
     - The token is injected with @Value("${app.security.token}"). Building the
       interceptor here means @WebMvcTest + @Import(WebConfig.class) picks it up
       automatically.

     6. GlobalExceptionHandler

     - New handlers for UnauthorizedException (401, plus the WWW-Authenticate: 
       Bearer header the HTTP spec requires on a 401) and for
       MissingCorrelationIdException (400).
     - Correlation id in error bodies: build(...) reads X-Correlation-Id from
       the current request (via RequestContextHolder) and passes it to a new
       ErrorResponse.of(code, message, correlationId) overload. The existing
       of(code, message) stays. This applies to every error response, including
       a 401 from the interceptor: if the request sent the header, the body
       includes it. If the header is missing or blank, the field is null and
       @JsonInclude(NON_NULL) omits it.
     - Catch more cases instead of returning 500: Spring MVC exceptions that
       don't have a handler yet, such as MissingServletRequestParameterException
       and HttpMediaTypeNotAcceptableException, implement
       org.springframework.web.ErrorResponse and carry their own status code. In
       the Exception catch-all, if ex instanceof 
       org.springframework.web.ErrorResponse, the response uses that status with
       a generic code (new ErrorCode.BAD_REQUEST-style entry, or a
       status-driven overload of build). Only truly unexpected errors still
       return 500.

     7. New controller/ApiErrorController.java (implements Spring Boot's 
     ErrorController, mapped to /error)

     This replaces Boot's BasicErrorController, which produces the whitelabel
     page and the {timestamp,status,error,path} JSON. Anything that never
     reaches DispatcherServlet or the advice (filter errors, response.sendError,
     container errors) gets forwarded by Tomcat to /error. This controller
     reads RequestDispatcher.ERROR_STATUS_CODE and returns ErrorResponse with
     the same JSON shape, without stack traces or messages.
     - application.properties: server.error.whitelabel.enabled=false as an extra
       safety net.
     - Known limit, to mention to the user: when a request is so malformed that
       Tomcat rejects it while parsing the HTTP request line, before Spring is
       involved at all, Tomcat itself answers. That only happens with raw
       garbage requests, never with normal API calls.

     Learning-mode contribution

     I write everything except the body of RequestHeadersInterceptor.preHandle,
     marked TODO(human), about 6–10 lines. The user decides:
     - the order of the checks: auth first (an unauthenticated caller learns
       nothing else) or correlation id first
     - how strict the bearer parsing is (case of Bearer, extra spaces)
     - comparing the token with equals or MessageDigest.isEqual (constant-time)

     Tests

     - Existing controller tests (AccountControllerTest,
       TransferControllerTest): every request now needs the two headers. Add a
       small shared test helper, for example
       controller/TestHeaders.withValidHeaders(MockHttpServletRequestBuilder),
       and use it in postJson and in each get(...). expectError currently
       asserts X-Correlation-Id doesNotExist. Change it to assert that the field
       equals the test correlation id.
     - New controller/RequestHeadersInterceptorTest
       (@WebMvcTest(AccountController.class) + @Import(WebConfig.class)):
       - no Authorization → 401 UNAUTHORIZED + WWW-Authenticate: Bearer
       - wrong token / Basic xyz / Bearer  with an empty token → 401
       - valid token, no X-Correlation-Id → 400 MISSING_CORRELATION_ID; blank
         value → 400
       - valid headers → 200, and the response echoes the X-Correlation-Id
         header
       - an error response body contains "X-Correlation-Id": "<sent value>"
       - the controller/service is never called on a rejected request
         (verify(..., never()))
     - New controller/ApiErrorControllerTest: a request to /error with the
       jakarta.servlet.error.status_code attribute set returns ErrorResponse
       JSON with the matching status.
     - Run ./mvnw test. All tests pass.

     Curls

     - New requests/auth-curls.sh, in the same style as the existing scripts:
       with BASE_URL, TOKEN="token-123" and CID="test-correlation-id-001", it
       covers valid / no auth / wrong token / wrong scheme / no correlation id /
       blank correlation id / unknown URL (JSON 404, not whitelabel).
     - Update limits-curls.sh and transfer-curls.sh to send both headers.
       Without them, every request in those scripts would now get 401.
     - Also show the main curls in the final reply so they're easy to copy.

     Verification

     1. ./mvnw test: all tests pass.
     2. ./mvnw spring-boot:run, then bash requests/auth-curls.sh. Check each
        status code and that every body is ErrorResponse JSON with the
        correlation id.

● The token gets there in three steps, and Spring only handles the first one:

  1. Spring reads the property: application.properties has
     app.security.token=token-123.
  2. Spring passes it to WebConfig: WebConfig is a Spring bean, so when Spring
     creates it, it resolves @Value on the constructor parameter:
  public WebConfig(@Value("${app.api.base-path}") String basePath,
                   @Value("${app.security.token}") String securityToken) {
  3. WebConfig passes it to the interceptor by hand: this is an ordinary new
     call in addInterceptors, not Spring injection:
  registry.addInterceptor(new RequestHeadersInterceptor(securityToken))

  By the time preHandle runs, expectedToken is just a regular final field set in
  the constructor. RequestHeadersInterceptor has no @Component or @Value, so
  Spring doesn't manage it as a bean. Spring only keeps the instance you gave it
  and calls it on each request.

    class with new RequestHeadersInterceptor("any-token"), without starting
