● Seed data means the starter rows put into the database every time the app
  starts. Your two test accounts would be seed data. Spring Boot does this for
  you: it runs src/main/resources/data.sql against the database on startup.
  Because H2 runs in memory and is wiped when the app stops, every start begins
  with the same two accounts. You don't need any hardcoded new Account(...) in
  Java. Both options below use the same data.sql. They only differ in who 
  creates the tables.

  ✶ Insight ─────────────────────────────────────
  Option A – schema.sql + data.sql, ddl-auto=validate
  - You write the CREATE TABLE statements yourself in schema.sql. Spring runs
    that file, then data.sql.
  - Hibernate doesn't create anything. On startup it checks that your @Entity
    classes match the real tables. If they don't (for example a missing column
    or the wrong type), the app fails to start.
  - You control the details exactly: account_number CHAR(26) NOT NULL UNIQUE,
    amount DECIMAL(17,2), FK names, indexes.
  - Moving to Flyway or Liquibase later is a simple step, because your schema is
    already plain SQL.
  - The cost: every entity change means editing both the Java class and the SQL.

  Option B – Hibernate DDL + data.sql, ddl-auto=create-drop
  - Hibernate reads your annotations and creates the tables itself. You need
    spring.jpa.defer-datasource-initialization=true so data.sql runs after the
    tables exist (by default it runs before).
  - Less to write. You add a field and the column appears.
  - The schema comes from annotations, so details like CHAR vs VARCHAR,
    constraint names or a FK index depend on how Hibernate reads
    @Column(length=26, nullable=false). Nothing catches a difference between
    what you intended and what got created. Real production systems almost never
    use this.
    ─────────────────────────────────────────────────

     edit
     Plan: In-memory H2 + JPA entities (Account, TransferHistory) with seed data

     Context

     The project keeps its only account hardcoded in Java (new Account() → id 1,
     balance 5000.00 in AccountService). The user wants an in-memory H2
     database to hold test data instead: JPA entities, an explicit schema, and
     two seed accounts loaded at startup. Scope (user's choice): entities + 
     config only. AccountService and TransferService keep using the in-memory
     account for now. Wiring them to the DB comes later.

     Decisions made with the user:
     - Schema is schema.sql + data.sql, with
       spring.jpa.hibernate.ddl-auto=validate, so Hibernate only checks that the
       entities match the DDL.
     - TransferHistory → Account is @ManyToOne through an FK column account_id.
     - TransferHistory gets an extra amount column, DECIMAL(17,2), which matches
       TransferRequest's @Digits(integer = 15, fraction = MoneyUtils.SCALE).

     Changes

     1. pom.xml

     - spring-boot-starter-data-jpa (compile)
     - com.h2database:h2 (scope runtime; the version comes from the Boot parent)
     - spring-boot-starter-data-jpa-test (scope test, for @DataJpaTest; already
       in ~/.m2, so the Boot 4 module name is confirmed)

     2. src/main/resources/application.properties (append)

     spring.datasource.url=jdbc:h2:mem:bank;DB_CLOSE_DELAY=-1
     spring.datasource.username=sa
     spring.datasource.password=
     spring.sql.init.mode=always            # run schema.sql then data.sql on 
     every start
     spring.jpa.hibernate.ddl-auto=validate # Hibernate checks entities against 
     schema.sql, never creates tables
     spring.jpa.open-in-view=false
     (The H2 console is left out: RequestHeadersInterceptor would demand Bearer
     + correlation headers on it anyway.)

     3. src/main/resources/schema.sql

     - account
       - id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
       - account_number VARCHAR(26) NOT NULL, with UNIQUE and CHECK 
         (CHAR_LENGTH(account_number) = 26). The column is VARCHAR, not CHAR:
         Hibernate maps String to varchar, so validate would reject a CHAR
         column. The CHECK constraint enforces "always 26".
       - balance DECIMAL(17,2) NOT NULL
       - transfer_limit DECIMAL(17,2) NOT NULL, limit_used DECIMAL(17,2) NOT 
         NULL. These are the embedded Limits. The column isn't called limit
         because that's a reserved word in H2.
     - transfer_history
       - id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
       - account_id BIGINT NOT NULL REFERENCES account(id), plus an index on it
       - counterparty_account_number VARCHAR(26) NOT NULL, with the same 26-char
         CHECK
       - amount DECIMAL(17,2) NOT NULL, CHECK (amount > 0)
       - executed_at TIMESTAMP(6) WITH TIME ZONE NOT NULL. The Java field is
         still timestamp, but TIMESTAMP is a keyword in H2, so the column gets a
         different name. Hibernate maps Instant to this type on H2; the first
         test run confirms it.

     4. src/main/resources/data.sql

     Two seed accounts. The inserts don't list id, so the identity column
     assigns ids 1 and 2. If the ids were inserted explicitly, H2 wouldn't
     advance the identity counter, and the next generated insert would hit a
     duplicate key.
     - 12345678901234567890123456, balance 5000.00, limit 10000.00, used 0.00
     - 65432109876543210987654321, balance 1000.00, limit 10000.00, used 0.00

     5. model/Account.java → @Entity @Table(name = "account")

     - @Id @GeneratedValue(strategy = IDENTITY) Long id
     - @Column(name = "account_number", length = 26, nullable = false, unique = 
       true) @Size(min = 26, max = 26) String accountNumber
     - @Column(precision = 17, scale = 2, nullable = false) BigDecimal balance
     - @Embedded Limits limits
     - Drop final from the fields, because JPA needs to set them.
     - Add @NoArgsConstructor(access = PROTECTED) for JPA.
     - Main constructor becomes Account(Long id, String accountNumber, 
       BigDecimal balance, Limits limits). It still calls MoneyUtils.normalize.
     - The hardcoded public Account() is removed. The default account moves into
       AccountService(): new Account(1L, "<26 chars>", new 
       BigDecimal("5000.00"), new Limits()). That keeps "hardcoded" logic out of
       the entity, and services stay in-memory as agreed.
     - debit() and the getters are unchanged.

     6. model/Limits.java → @Embeddable

     - @Column(name = "transfer_limit", precision = 17, scale = 2) limit and
       @Column(name = "limit_used", ...) used.
     - Drop final. The existing public Limits() stays (it serves as the JPA
       no-arg constructor too).
     - remaining becomes derived (limit - used) and isn't stored, so the used + 
       remaining == limit invariant can't drift in the DB. During implementation
       this will be a TODO(human) Learn-by-Doing piece: the user decides
       between stored and computed remaining, and implements getRemaining() /
       allow / use.

     7. New model/TransferHistory.java → @Entity @Table(name = 
     "transfer_history")

     - @Id @GeneratedValue(IDENTITY) Long id
     - @ManyToOne(fetch = LAZY, optional = false) @JoinColumn(name = 
       "account_id", nullable = false) Account account
     - @Column(name = "counterparty_account_number", length = 26, nullable = 
       false) String counterpartyAccountNumber
     - @Column(precision = 17, scale = 2, nullable = false) BigDecimal amount,
       normalized via MoneyUtils.normalize
     - @Column(name = "executed_at", nullable = false) Instant timestamp
     - @Getter, a protected no-arg constructor, and a public constructor taking
       all fields except id.

     8. New repository/AccountRepository, repository/TransferHistoryRepository

     These are plain JpaRepository<…, Long> interfaces. Only tests use them for
     now. They aren't wired into the services (out of scope).

     9. Test updates

     - AccountTest, TransferServiceTest: change new Account(1L, balance, limits)
       to the new 4-arg constructor. Move
       defaultAccountHasHardcodedValuesWithTwoDecimalPlaces to
       AccountServiceTest, since the default now lives in AccountService.
     - New repository/PersistenceTest (@DataJpaTest):
       - the seed data loads 2 accounts with the expected numbers and balances
       - a saved TransferHistory can be read back with its account, and amount
         keeps scale 2 (compared with compareTo)
       - an account number that isn't 26 characters is rejected
